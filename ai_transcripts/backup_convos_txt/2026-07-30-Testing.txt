The core idea: "real" tests vs smoke tests
A smoke test just checks that something renders or doesn't crash. What the rubric wants is tests that exercise real behaviour — call an actual function, with actual inputs, and assert on the actual output or side effect. For your app that means things like:

Call archiveTask(id) → then call getTasks() → assert the archived task is not in the active list but is in getArchivedTasks().
Construct a task with a due date in the past and status Todo → run it through toTask() (or wherever overdue is derived) → assert overdue === true.
Both of those touch real logic, not rendering.

The throwaway database problem
This is the part people usually get wrong first. If your tests hit data/app.db, two bad things happen: tests leave junk in your real data, and tests aren't deterministic (results depend on whatever's already in the DB). The rubric explicitly penalises this.

Now let's set up the throwaway-database pattern before writing that first test, since every test file needs it.

The problem with a naive test
If you just write:

ts
import { archiveTask } from '@/actions/tasks';
...at the top of a test file, Node runs db.ts immediately (import side effects), which opens data/app.db — your real file — before your test gets a chance to set SQLITE_PATH. Import order matters here: the env var has to exist before db.ts is first evaluated.

The fix: a setup file that runs first
Create vitest.setup.ts at the project root:

ts
import fs from 'fs';
import path from 'path';

const testDbPath = path.join(process.cwd(), 'test.db');

// Wipe any leftover file from a previous crashed run
if (fs.existsSync(testDbPath)) fs.unlinkSync(testDbPath);

process.env.SQLITE_PATH = testDbPath;
A couple of deliberate choices here, worth understanding rather than just pasting:

A real temp file, not :memory:. better-sqlite3's :memory: mode works, but each new Database(':memory:') call gets its own isolated database — and because Next.js Server Actions can each pull in a fresh module instance in some setups, that risks two parts of your test accidentally talking to different in-memory databases with no error, just silently wrong results. A real file on disk is one database, guaranteed, and it's deleted automatically anyway (see below) — so you don't pay a real cost for the extra safety.
Deleted before the run, not after. If a previous test run crashed mid-way, an old test.db could linger and leak state into the next run. Cleaning up before is more reliable than relying on an afterAll that might not fire.
Now wire it into the config:

diff
 export default defineConfig({
   test: {
     environment: 'node',
+    setupFiles: ['./vitest.setup.ts'],
   },
 });
setupFiles runs before any test file's imports are evaluated, which is exactly the ordering we need.

Walk through why each part is there, since this is the pattern every other test will follow:

beforeEach clearing the table. This is what makes the test deterministic — the rubric's word, not mine. Without it, running the suite twice in a row gives you two tasks instead of one, and activeBefore[0] might not be the task you think it is.

This is a classic gotcha, not a mistake in the test itself — worth understanding since you'll hit variants of it again.

Why it happens: @/* isn't a real Node.js feature — it's a path alias that only means something to whatever tool is told to resolve it. Next.js's own bundler reads tsconfig.json's paths config and rewrites @/lib/db to the real file automatically. Vitest runs on Vite, a completely separate bundler, and Vite doesn't read tsconfig.json by default — so @/lib/db means nothing to it, hence "cannot find package."

Two ways to fix it. I'd go with the plugin — it's one line and stays correct automatically if your folder structure ever changes:

Option A — vite-tsconfig-paths plugin (recommended):

bash
npm install -D vite-tsconfig-paths
diff
 import { defineConfig } from 'vitest/config';
+import tsconfigPaths from 'vite-tsconfig-paths';

 export default defineConfig({
+  plugins: [tsconfigPaths()],
   test: {
     environment: 'node',
     setupFiles: ['./vitest.setup.ts'],
   },
 });
This reads your existing tsconfig.json paths entry and makes Vite (and therefore Vitest) understand @/* the same way Next.js does — no alias logic duplicated, one source of truth.

Option B — hardcode the alias manually in the config, no new dependency, but you'd be maintaining the same mapping in two places (tsconfig.json and vitest.config.ts) and it'll silently drift if one changes and not the other. I wouldn't recommend it here, but flagging it since you might prefer fewer dependencies — your call.

If you go with A, add vite-tsconfig-paths to docs/third-party-code.md too — it's a real dependency of the project now, and the rubric explicitly wants every installed package justified.

This one's not about your code being wrong — it's Next.js's Server Action machinery bumping into the fact that Vitest isn't Next.js.

Why it happens: revalidatePath() is Next.js's cache-invalidation call. Normally when a Server Action runs, it's inside an active Next.js request — there's a "static generation store" tracking that request, and revalidatePath needs that store to know what to invalidate. When Vitest calls createTask() directly, there's no Next.js server running at all — no request, no store — so revalidatePath throws immediately, before your actual insert logic even finishes.

Your test isn't testing caching behaviour — it's testing "did the row get archived correctly." So the right fix is to replace revalidatePath with a no-op during tests, not to work around the real one.

Add this to vitest.setup.ts:

ts
import { vi } from 'vitest';

vi.mock('next/cache', () => ({
  revalidatePath: vi.fn(),
}));
diff
 import fs from 'fs';
 import path from 'path';
+import { vi } from 'vitest';
+
+vi.mock('next/cache', () => ({
+  revalidatePath: vi.fn(),
+}));

 const testDbPath = path.join(process.cwd(), 'test.db');
Since this is in setupFiles, it applies before every test file's imports run, so any Server Action calling revalidatePath — createTask, updateTask, archiveTask — gets the mock automatically. vi.fn() is a fake function that does nothing but silently records that it was called, in case you ever want to assert "yes, revalidation was triggered" — you don't need that for this test, but it's there if a later one wants it.

Nothing's broken — the plugin still works — but if you want to simplify later you could delete it and set resolve.tsconfigPaths: true directly. For unit/integration tests (testing functions directly — what we're doing):

function startOfDay(d: Date): Date {
  return new Date(d.getFullYear(), d.getMonth(), d.getDate());
}

/**
 * Whole calendar days between a due date and today.
 * Negative = due date already passed. 0 = due today. Positive = still upcoming.
 * This is the single source of truth for "overdue" across the app —
 * both dueStatus.ts and types.ts call this rather than each doing their own math.
 */
export function daysUntilDue(dueDateStr: string): number {
  const due = startOfDay(new Date(dueDateStr));
  const today = startOfDay(new Date());
  return Math.round((due.getTime() - today.getTime()) / 86400000);
}
This lives on its own, with no import from types.ts — deliberately, to avoid a circular import (dueStatus.ts already imports TaskStatus from types.ts; if types.ts imported back from dueStatus.ts, that's a cycle. Routing both through a neutral third file avoids it entirely).

just a quick check is it convention for all tests to be in one file?

Not a strict rule, but the common convention is one test file per source file, colocated or mirrored — e.g. dueStatus.ts → dueStatus.test.ts, date.ts → date.test.ts, tasks.ts → tasks.test.ts (which you already have). Two flavours of where they live:

Colocated — test file sits right next to the source file, same folder. What we're doing (src/actions/tasks.test.ts next to src/actions/tasks.ts). Easiest to find, most common for smaller projects.
Mirrored __tests__ or tests/ folder — a separate directory tree that mirrors src/. More common in larger codebases where you want source and tests visually separated.
For a project this size, one file per module (colocated) is the right call — it's what Vitest's docs assume by default, and it keeps each test file focused on one thing, which makes it obvious at a glance what's covered and what isn't (useful for you right now, and for whoever's marking against that rubric's "tests exercise real behaviour" criterion — one glance at the file list shows archiving, overdue, etc. each has a home).

One giant all.test.ts isn't wrong, exactly, but it gets unwieldy fast and makes git diff noisier when you touch one feature's tests.

Good catch — yes, exactly right. Every one of the getDueFlag tests already calls daysUntilDue under the hood, so in one sense it's already being exercised, and a separate date.test.ts would technically be testing something you've already got coverage of.

But there's a real distinction between "exercised" and "directly verified," and it matters here specifically:

getDueFlag's tests check the combination of rules — day math plus the "Complete" short-circuit plus the "archived" short-circuit. If one of those tests fails, you don't immediately know which piece broke — the day math, or one of the short-circuits.
A direct daysUntilDue test isolates just the boundary math, with no other logic in the way — e.g. does a task due today return exactly 0, not 1 or -1? Does a task due exactly 7 days out land as 7? Those are easy to get subtly wrong (off-by-one on the boundary is the classic bug), and a direct test pinpoints that specific line if it regresses, rather than you having to go re-derive it from a getDueFlag failure.
Think of it as: getDueFlag tests prove the feature behaves correctly; a daysUntilDue test proves the building block is correct on its own, independent of anything built on top of it. If you ever add a second thing that uses daysUntilDue later (say, sorting tasks by urgency), you'd want that foundation already independently trustworthy rather than only proven-by-implication through one caller.

That said — for a project this size, hitting 3+ tests with real coverage is the actual bar, not textbook completeness. If you'd rather spend the time budget elsewhere (e.g. a createTask/updateTask test, or writing docs), skipping a dedicated date.test.ts and relying on the indirect coverage is a defensible call, not a wrong one.

prepare/run — yes, exactly right. db.prepare(sql) compiles the SQL once (with ? placeholders standing in for values) and returns a reusable statement object; .run(values) executes it with the actual values slotted in. Two reasons it's split like that rather than one call: performance (SQLite can reuse the compiled query instead of re-parsing SQL text every time), and safety — plugging values in via placeholders instead of string-concatenating them into the SQL avoids SQL injection. You'll also see @title-style named placeholders elsewhere in tasks.ts (e.g. createTask) — same mechanism, just matched by object key instead of position.

Is this seriously all the backend? — yes, genuinely. This is the actual shape of a Next.js Server Actions app: there's no separate Express server, no /api routes, no controllers. src/actions/tasks.ts's exported functions are the backend — React components call them directly (await createTask(...)), and Next.js handles the client↔server boundary invisibly under the hood. So the backend is exactly: db.ts (connection), schema.ts (table), tasks.ts (the four operations), plus types.ts/dueStatus.ts/date.ts for the derived logic. That's the whole thing — not a stub, not missing pieces. Good to know cold for database-design.md, since a reader might expect a routes folder that doesn't exist.

Is your DB already set up? — yes, automatically, and it's worth understanding why: db.ts calls initSchema(db) at module load time (not inside any function — it just runs when the file is imported), and initSchema uses CREATE TABLE IF NOT EXISTS.
