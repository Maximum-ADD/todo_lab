Silent death with zero stack trace usually points to the process being killed rather than crashing on its own — Node doesn't normally exit silently on errors, something else is terminating it.

Things to check, roughly in order of likelihood:

1. Out-of-memory kill (most common cause of this exact symptom)
Turbopack compiling the first page can spike memory, and on a small VM it gets OOM-killed with no application-level error at all — the shell just returns to prompt.

bash
dmesg | tail -30
or

bash
journalctl -k -n 50 | grep -i "killed process"
If you see "Out of memory: Killed process ... node", that's your answer. Check available memory with free -h.

2. Check the actual exit code
Run it directly (not through npm run) so you can see the exit status clearly:

bash
next dev
echo $?
An exit code of 137 = SIGKILL (OOM or manual kill). 139 = segfault.

3. Try without Turbopack
Turbopack is newer/less battle-tested than webpack. Rule it out:

bash
npx next dev --no-turbo
or edit the dev script in package.json to drop --turbopack if it's there.

4. Clear cache and node_modules
Corrupted .next cache or a bad native binary (especially after a Node/npm version change) can cause this:

bash
rm -rf .next node_modules
npm install
npm run dev
5. Node version

bash
node -v
Next.js 16 needs a fairly recent Node — if you're on something old/unsupported, native module mismatches can crash silently.

Good news: npx next dev exited with code 0 — that's not a crash, kill, or OOM. Code 0 means the process believes it finished successfully and exited on its own. That's actually the real mystery: next dev is supposed to run forever as a server, not exit cleanly right after "Compiling /".

One thing stands out in your npm install output:

npm warn EBADENGINE Unsupported engine {
  package: 'better-sqlite3@13.0.2',
  required: { node: '>=22' },
  current: { node: 'v20.20.2', npm: '10.8.2' }
}
better-sqlite3 is a native (compiled) module. If it was built against a Node ABI version your current Node (20.20.2) doesn't match, requiring it can silently misbehave in odd ways — and "Compiling /" is exactly the point where Turbopack starts evaluating your root page/route, which is likely where a database connection (using better-sqlite3) gets initialized.

Steps to confirm and fix:

1. Confirm the server is actually dead, not just returning your prompt oddly
Right after it prints "Compiling /" and returns you to the shell, open a second terminal and run:

bash
curl -I http://localhost:3000
If that fails to connect, the server really did exit.

2. Try requiring better-sqlite3 directly to see if it throws

bash
node -e "require('better-sqlite3')"
If this errors (e.g. NODE_MODULE_VERSION mismatch or a .node binding load failure), you've found it.

3. Upgrade Node to match the required engine

bash
nvm install 22
nvm use 22
rm -rf node_modules .next
npm install
npm run dev
4. If you can't upgrade Node right now, try rebuilding the native module against your current Node instead:

bash
npm rebuild better-sqlite3
Run step 2 first — it'll take 10 seconds and tell us definitively whether that's the culprit before you go through a Node upgrade.

A couple of notes worth folding in too, since they'll save the next person (or future you) the same debugging loop:

If someone's shell is zsh instead of bash, source ~/.bashrc won't pick up nvm — they'd need source ~/.zshrc instead. Worth a one-line callout.
After switching Node versions, a stale node_modules built against the old ABI can cause silent failures — so rm -rf node_modules .next && npm install is a good "if things act weird" fallback to mention.
Consider adding an .nvmrc file with 22 in the repo root — then people (and CI) can just run nvm use with no version number, and nvm will auto-pick it up if their shell is configured for it.
