Since you're new to SQLite, let me walk you through the basics as we build the connection layer.

What SQLite actually is
SQLite isn't a server you run (like Postgres or MySQL) — it's just a file. Your whole database lives in one .db file on disk. better-sqlite3 is a library that lets Node.js read and write that file directly, no network connection involved. That's exactly why it's a great fit for a local-first app.

The four SQL commands you'll use 90% of the time
sql
CREATE TABLE todos (...)   -- define the shape of your data (once)
INSERT INTO todos (...)    -- add a row
SELECT * FROM todos        -- read rows
UPDATE todos SET ...       -- change a row
DELETE FROM todos WHERE... -- remove a row
Step 1: The connection file
This is the one place your app opens the database. Everything else imports from here.

Create lib/db.ts (or src/lib/db.ts if you used the src/ directory):

typescript
import Database from 'better-sqlite3';
import path from 'path';

// The .db file will be created in your project root the first time this runs
const dbPath = path.join(process.cwd(), 'data', 'app.db');

// Ensure the data folder exists
import fs from 'fs';
const dataDir = path.join(process.cwd(), 'data');
if (!fs.existsSync(dataDir)) {
  fs.mkdirSync(dataDir);
}

const db = new Database(dbPath);

// Recommended pragmas for a local single-user app
db.pragma('journal_mode = WAL'); // faster, safer writes

export default db;
A few things worth understanding here:

new Database(dbPath) opens the file if it exists, or creates a brand new empty one if it doesn't. You don't need to "install" or "create" the database separately — this line does it.
WAL mode (Write-Ahead Logging) is a setting that makes reads and writes play nicer together. It's the standard recommendation for better-sqlite3 and costs you nothing to enable.
This file should only ever be imported by server-side code (API routes, Server Actions) — never by client components. SQLite can't run in the browser.

"Scaffolding" is the skeleton of a project before you fill in real features — folders, empty files, and a couple of stub components that establish where things go and how the pieces connect, without yet building any actual todo logic. Think of it like the frame of a house before walls and paint: it tells you where the kitchen goes, but there's no fridge in it yet.

For a Next.js + SQLite app, scaffolding usually means:

The folder structure (pages, components, database layer, styles)
A base layout that wraps every page
One empty/placeholder page
The database connection file (which you already have working)
A schema file defining your tables
A thin layer for reading/writing data — as either Server Actions or API routes
One thing to nail down before I build this: earlier I asked whether you wanted Server Actions or API routes and it got skipped over. For a local-first, single-user app like yours, I'd lean toward Server Actions — they're the more modern Next.js approach, mean less boilerplate (no separate /api endpoints to write and fetch from), and fit a simple local app well. Why they want it

That your AI usage matches what you said you used it for in the README/commits.
The "AI usage" rubric row's top mark specifically requires evidence of you catching and correcting a bad AI output — the transcript is where that evidence lives.
How to get one from this conversation
Claude.ai doesn't currently have a one-click "export transcript" button, so the practical options are:

Share link: use the share button on this conversation to generate a link, and include that link in your submission.
Copy/paste into a file: copy the whole conversation into a markdown or text file and include it in your repo (e.g. transcripts/session-1-scaffolding.md).
Screenshots, only as a last resort if the above aren't feasible — the policy explicitly says to use a tool's export function or "the saved files of the tool" if no export exists.
Practical tips
Don't wait until submission day to gather these — save/export each session as you finish it, especially ones with real debugging (like the better-sqlite3 build error we worked through, or the extraneous/devDependencies fixes) — those are good "AI usage" evidence because you're the one who caught the problem and I helped fix it, not the other way around.
