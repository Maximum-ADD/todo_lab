On "does two things"
Single Responsibility usually means "one reason to change," not "no branching." findOrCreateTopicId has exactly one reason to change: how a topic name gets resolved to a stable id. That's one job, named accurately — the "or" in the name isn't hiding two responsibilities, it's honestly describing the one thing it does: idempotent resolution.

If you split it into findTopicId and createTopic, the "check, then decide" logic doesn't disappear — it just moves to every call site that needs a topic id, which then has to write the same find ?? create pattern themselves. You'd be trading one tested function for N untested copies of the same branching logic scattered through the codebase. That's usually a worse trade, not a better one.

If your actual worry is testability (wanting to test "find" and "create" independently), there's a middle path — keep the convenience function, but build it out of two small named pieces:

typescript
function findTopicId(db: Database.Database, name: string): number | null {
  const row = db.prepare(`SELECT id FROM topics WHERE name = ?`).get(name) as
    | { id: number } | undefined;
  return row?.id ?? null;
}

function createTopic(db: Database.Database, name: string): number {
  const result = db.prepare(`INSERT INTO topics (name) VALUES (?)`).run(name);
  return Number(result.lastInsertRowid);
}

export function findOrCreateTopicId(db: Database.Database, name: string): number {
  return findTopicId(db, name) ?? createTopic(db, name);
}
That's a genuine improvement if you want it — each piece becomes independently readable — but I wouldn't call the original a design flaw. Your call; I'll test whichever version you actually keep.
